# parakram_comms — comms fabric, QoS by message class, loss injection (CLAUDE_CODE/05)

## QoS profiles (`qos.py`, imported by every PARAKRAM publisher / subscriber)

| profile | policies | topics |
|---|---|---|
| `STATE_QOS` | BEST_EFFORT, VOLATILE, KEEP_LAST 1 | `/<ns>/state` |
| `INTENT_QOS` | BEST_EFFORT, VOLATILE, KEEP_LAST 5 | `/<ns>/intent` |
| `TASK_QOS` (= `TASK_POOL_QOS`) | RELIABLE, TRANSIENT_LOCAL, KEEP_ALL | `/fleet/tasks`, task announcements, awards, completions (04) |
| `TASK_EVENT_QOS` | RELIABLE, VOLATILE, KEEP_LAST 100 | bids, lease renewals (04: only their latest values matter) |
| `HEARTBEAT_QOS` | BEST_EFFORT, VOLATILE, KEEP_LAST 5, liveliness MANUAL_BY_TOPIC, lease `HEARTBEAT_LEASE_S` = 2 s | `/<ns>/heartbeat` (published by 06; the lease is a placeholder until 06 fixes L) |
| `STATUS_QOS` | RELIABLE, VOLATILE, KEEP_LAST 10 | `/<ns>/coord_status` (diagnostics, not a coordination input) |

State and intent are BEST_EFFORT so that loss shows up as staleness and is never hidden by
retransmission; the loss benchmark depends on it. Task/award state is RELIABLE +
TRANSIENT_LOCAL so that a (re)joining robot replays the current task pool. Neither the reactive
safety layer (03) nor the spatial leases (02) wait on any RELIABLE topic.

## App-level loss injection (`loss.py`, the primary mechanism)

`LossFilter` wraps the coordination node's subscriptions to its peers' `state` and `intent` and
drops a message BEFORE it is processed. Each (receiver, sender, topic) stream has its own RNG
seeded from the run's integer seed and the stream name (SHA-256), so a run with the same seed
drops the same message indices. Models:

- `bernoulli` (default): each message is dropped with probability `loss`.
- `gilbert_elliott`: bursty two-state Markov chain with stationary loss `loss` and lag-1
  correlation `burst_corr` (0.8 by default, per CLAUDE_CODE/07): mean burst 1 / ((1 - loss)(1 - rho)).

```bash
ros2 launch parakram_bringup fleet_sim.launch.py n_robots:=3 scenario:=intersection seed:=1 loss:=0.3
ros2 launch parakram_coord coord.launch.py n_robots:=3      # takes loss/seed from the run manifest
# bursty: add loss_model:=gilbert_elliott [loss_burst_corr:=0.8] to fleet_sim
```

`loss` is recorded in `run_manifest.json` and `coord_manifest.json`; every coordination node
appends its counters to `bench/logs/<run_id>/comms_<ns>.csv` every 5 s and at shutdown:

| column | meaning |
|---|---|
| `received` | messages the transport delivered on that peer stream |
| `dropped` / `passed` | discarded by the injector / processed by coordination |
| `first_seq`, `last_seq` | the sender's seq span seen (= messages it published meanwhile) |
| `drop_bursts` | runs of consecutive drops (`dropped / drop_bursts` = mean burst length) |
| `loss`, `model`, `burst_corr`, `seed` | the setting |

Never applied to: task/award traffic (RELIABLE, 04), heartbeats, the safety layer's inputs (it
reads no peer traffic), the dashboard or the ground-truth monitor.

The network-level mechanism (`tc netem`) and the Benchmark #2 sweep live in `parakram_bench`
(see its README).

## Fabrics: how to switch

PARAKRAM nodes are plain rclpy with the profiles above; the fabric is chosen per shell.

### rmw_zenoh, one router per robot (the primary fabric)

Each robot runs its own `rmw_zenohd`; every router connects to every other robot's router, so
the routers form a full mesh with no central server. A robot's nodes connect to their own
router (peer mode). `config/zenoh_router_<robot>.json5` / `zenoh_session_<robot>.json5` are
generated by `parakram_comms.zenoh_mesh` from the installed rmw_zenoh_cpp defaults (only the
listen / connect endpoints differ); the committed ones are the single-host sim layout
(robot1 / 2 / 3 on 127.0.0.1:7447 / 7448 / 7449).

```bash
export RMW_IMPLEMENTATION=rmw_zenoh_cpp
CFG=$(ros2 pkg prefix parakram_comms)/share/parakram_comms/config
ros2 launch parakram_comms zenoh_routers.launch.py robots:=robot1,robot2,robot3   # sim: all 3
export ZENOH_SESSION_CONFIG_URI=$CFG/zenoh_session_robot1.json5   # in every robot1 shell
```

Hardware: generate the configs for the robots' addresses and start only the local router on
each robot:

```bash
python3 -m parakram_comms.zenoh_mesh --listen-all --out ~/zenoh \
    --robots robot1=<ip1>,robot2=<ip2>,robot3=<ip3>
ros2 launch parakram_comms zenoh_routers.launch.py robots:=robot1 config_dir:=$HOME/zenoh
export ZENOH_SESSION_CONFIG_URI=$HOME/zenoh/zenoh_session_robot1.json5
```

The router-free alternative of the work order (`ZENOH_ROUTER_CHECK_ATTEMPTS=-1` + multicast
scouting, e.g. `ZENOH_CONFIG_OVERRIDE='scouting/multicast/enabled=true'`) depends on multicast,
which WiFi access points often filter; the router mesh does not.

Checked live on the single-host sim layout (rmw_zenoh_cpp 0.2.10, evidence in
`bench/w05_evidence/`): the three routers connect pairwise; robot1 -> robot3 delivered 201/201
intents (BEST_EFFORT) and task messages (RELIABLE) at ~0.7 ms; with router2 killed the flow
continued; with robot1's own router killed robot1 was cut off (nothing delivered for 11 s: the
robot-loses-its-router case, where its reactive layer and leases carry it) and it rejoined within
~1 s of the router's restart (100/100).

Measured rmw_zenoh 0.2.10 behaviour that matters here:

- **TRANSIENT_LOCAL + KEEP_ALL replays only the last 10 samples** of each writer to a late
  joiner (KEEP_LAST N replays N; Fast DDS and CycloneDDS replay all of KEEP_ALL). With `TASK_QOS`
  (KEEP_ALL, as specified) a robot that (re)joins over Zenoh gets only the last 10 samples of
  each task-pool writer.
- **Liveliness QoS is accepted but raises no liveliness events** (`HEARTBEAT_QOS` messages are
  delivered; Fast DDS / CycloneDDS report alive -> not alive): a watchdog on Zenoh must count
  heartbeat messages.
- **Every stream rides a TCP link** (the rmw_zenoh default), BEST_EFFORT included, and TCP does
  not degrade gracefully under packet loss. Measured with netem on `lo`
  (`bench/logs/netem_check_0fe10780`; the probe's data took one direct peer-to-peer TCP link,
  one lossy hop like the DDS cases): at 30 % independent loss only 17 % of the BEST_EFFORT
  intents reached the subscriber within the 40 s window plus a 10 s drain, and those arrived in
  stale bursts between stalls of 10 s or more (median 0.33 s late, up to 18 s); at 60 % none
  did, and the link had still not recovered 10 s after the loss was removed (TCP retransmission
  backoff). Over UDP the DDS fabrics delivered ~1 - loss (Fast DDS 0.72 / 0.38, CycloneDDS 0.71 /
  0.40). On Zenoh a lossy link therefore behaves like an intermittent partition, not like
  graceful staleness: BEST_EFFORT at the ROS QoS level is not best effort at the link level.
- Consequences: PARAKRAM tolerates silence by design (leases expire, the reactive layer is
  local, stale intents carry an already-expired `lease_expiry`), but a network-level loss
  benchmark run over Zenoh is a benchmark over TCP, which CLAUDE_CODE/05 rules out; the loss
  benchmarks use the app-level drop, which acts after delivery and so is the same on every
  fabric. Caveats: loopback netem drops every packet independently (ACKs included) on a single
  host; real 802.11 retries frames at the MAC layer and loses in bursts, so the WiFi rig has to be
  measured (the CLAUDE_CODE/07 fabric ablation) before anything is said about Zenoh on WiFi.

### CycloneDDS with static unicast peers (the fallback)

```bash
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
export CYCLONEDDS_URI=file://$(ros2 pkg prefix parakram_comms)/share/parakram_comms/config/cyclonedds.xml
export PARAKRAM_PEER1=<ip1> PARAKRAM_PEER2=<ip2> PARAKRAM_PEER3=<ip3>   # default 127.0.0.1
```

Multicast off, discovery by unicast to the listed peers only (serverless). Checked on this host:
delivery, TRANSIENT_LOCAL KEEP_ALL replay (50/50) and liveliness events.

### Fast DDS (the ROS 2 default; the CLAUDE_CODE/05 sweep ran on it)

Nothing to set. Same-host traffic uses shared memory, so netem on `lo` cannot reach it.
